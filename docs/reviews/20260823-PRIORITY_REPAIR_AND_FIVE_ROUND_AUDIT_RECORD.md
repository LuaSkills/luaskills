### A04：下载缓存键可逃逸缓存根目录

- 分类：实际安全 BUG，必须修改。
- 事实链：公开 `DownloadRequest.cache_key` / `fetch_text*` 参数未经约束，直接进入 `cache_root.join(format!(...))`；`../`、反斜杠或绝对路径前缀可改变目标父目录。
- 修复：缓存文件名改为完整缓存键的 SHA-256 十六进制摘要，再拼接白名单 URL 后缀。
- 修改后收益：调用方无法通过缓存键控制路径分隔符或绝对前缀；同一键仍保持确定性，同目标并发锁语义不变。
- 连带影响：旧版本的可读缓存文件名不会命中新版本摘要路径，升级后首次请求会重新下载一次；缓存路径本身不是公开持久化契约。
- 复验：新增父级遍历与反斜杠回归测试；下载模块 21 项通过、1 项显式性能测试忽略。

### A05：下载进度回调重入导致目标锁死锁或工作池饥饿

- 分类：实际并发 BUG，属于本轮重构引入的必须修复项。
- 事实链：下载器持有同目标互斥锁并在固定 HTTP 工作线程中同步调用公开进度回调；回调重入相同缓存目标会等待自身外层锁，四个工作线程同时在回调中提交嵌套任务时会全部阻塞等待队列中的任务。
- 修复：进度回调作用域记录当前活动缓存目标，同目标重入在加锁前返回明确错误；固定工作线程安装线程局部共享 Client，使不同目标的嵌套 HTTP 任务在当前工作线程内联执行。
- 修改后收益：消除同目标永久等待和固定工作池完全饥饿；正常非重入下载、进度回调和连接池复用保持不变。
- 约束：同目标回调重入的发布语义本身存在歧义，因此显式拒绝，不采用递归覆盖或静默复用旧缓存。
- 复验：`progress_callback_rejects_same_target_reentry_without_blocking_outer_download` 与 `saturated_http_workers_complete_nested_tasks_without_pool_starvation` 均通过；严格 Clippy 通过。

### A06：tar.gz 安装链路重复进行两层全量内存缓冲

- 分类：逻辑性修复 / 性能优化，真实存在但不是功能 BUG。
- 事实链：`install_from_tar_gz_archive` 先用 `fs::read` 把整个压缩包读入 `Vec`，再把每个命中 tar 条目 `read_to_end` 到另一个 `Vec`，最后才复制到目标文件；两次全量驻留均不是归档 API 或导出契约所要求。
- 修复：直接用 `File` 构造 `GzDecoder`，并通过 `std::io::copy` 把命中条目流式写入目标文件。
- 修改后收益：压缩包和单个导出文件不再分别产生大小同阶的额外内存峰值；错误传播、导出匹配和可执行位处理保持不变。
- 复验：归档模块 6 项测试通过，严格 Clippy 通过。

### A07：技能更新发布失败时吞掉旧版本回滚失败

- 分类：实际事务与诊断 BUG，必须修改。
- 事实链：更新流程先把当前技能目录移动到备份，再把新目录移动到规范目标；第二次重命名失败时会尝试恢复备份，但原实现使用 `let _ = fs::rename(...)` 丢弃回滚结果。若发布和回滚同时失败，调用方只收到发布错误，而规范目标目录可能缺失，磁盘状态已经不确定。
- 修复：把新版本发布与旧版本恢复收敛到 `publish_staged_skill_update`；发布失败后仍恢复旧包，回滚也失败时在同一错误中包含备份路径、回滚错误和 `skill disk state is uncertain` 明确信号。
- 修改后收益：恢复成功时保持原事务语义；恢复失败时不再把严重状态破坏误导成普通发布失败，上层可停止后续提交并进行人工恢复。
- 复验：两个确定性文件系统测试分别覆盖“新目录缺失但备份恢复成功”和“新目录、备份均缺失导致双重失败”，共 2 项通过；连续计数清零。

### A08：单次进程执行绕过统一进程树，超时可能遗留后代并无限等待管道

- 分类：实际资源与生命周期 BUG，必须修改。
- 事实链：`vulcan.process.exec` 与托管 `io.popen` 均直接 `Command::spawn`；超时分支只对直接 `Child` 调用 `kill`，`process.exec` 还把 kill 与有界 wait 错误转换成空状态。若 shell/程序派生后代且后代继续持有 stdout 管道，直接子进程退出或 kill 后的 reader `join` 仍可无限等待，显式 `timeout_ms` 失去上界，并可能遗留进程。
- 修复：两条单次执行路径统一改用现有 `ManagedChildProcessTree::spawn_with_keepalive`；新增 `finalize_one_shot_process_tree`，统一完成整树终止、直接子进程后备 kill、5 秒有界回收、Windows Job 收敛检查及无法同步收敛时的静态 reaper 所有权交接。直接子进程自然退出后也会清理仍存活的后代，避免继承管道悬挂。
- 修改后收益：显式超时不再因为后代持管道而退化为无界等待；两条分支不再各自吞掉进程清理错误或丢弃 `Child` 所有权；正常 stdout 完整返回与编码契约保持不变。
- 连带影响：单次执行 API 不再允许根进程退出后把后台后代留在宿主中继续运行；需要持久进程的调用方应使用已有 `vulcan.process.session`，该变化属于对单次执行所有权边界的修正。
- 复验：确定性进程树测试构造“根进程退出、后代继续持有继承管道 120 秒”的场景，统一收尾在约 0.17 秒内终止后代并通过；`process.exec` 50ms 超时测试、managed_io 16 项测试通过；严格 Clippy 通过。

### A09：Provider 动态库加载重复探测且重复输出同一错误

- 分类：逻辑性修复 / 明显冗余验证，不是功能扩展。
- 事实链：SQLite 与 LanceDB 加载器均先调用 `Path::exists()`，随后 `Library::new` 再次访问同一路径；预检与真实加载之间存在 TOCTOU 窗口，且 `exists()` 会把权限/元数据错误折叠成“不存在”。真实加载失败时格式串还把同一个 `error` 连续输出两次。
- 修复：新增共享 `load_provider_dynamic_library`，两类 Provider 都直接执行一次真实动态加载；错误统一包含 Provider 名、宿主可见路径和一次原生加载器诊断。
- 修改后收益：每次初始化少一次无必要文件系统探测，缺失、权限、格式和传递依赖错误不再被预检误导；两条分支的错误格式不再漂移或重复。
- 复验：共享加载器、SQLite、LanceDB 三项缺失库测试通过，均验证稳定前缀来自真实加载入口；严格 Clippy 将在本轮收尾再次执行。

### A10：技能根目录先做 metadata 预检再立即 read_dir

- 分类：逻辑性修复 / 明显冗余验证，不是功能 BUG。

- 复验：非法路径与文件型技能根两项错误保真测试通过；缺失根语义继续由有效实例收集测试覆盖。

### A11：依赖导出目标路径可逃逸安装根目录

- 分类：实际安全 BUG，必须修改。
- 事实链：`DependencyExportSpec.target_path` 由技能 `dependencies.yaml` 或远程 skilllist 反序列化并完成模板替换后，安装器和存在性检测都直接执行 `install_root.join(...)`；清单加载、请求解析和最终写入入口均没有相对路径约束。`../`、反斜杠父目录、根路径、UNC/设备路径及 Windows 驱动器路径可以改变目标归属，原始文件、ZIP、tar.gz 三条安装分支均受影响。

- 修改后收益：不可信依赖声明不能把下载内容写出宿主管理根目录，检测也不能探测根外文件；全局预解析确保后面的非法声明不会在前面声明已经写盘后才被发现，同时消除各归档分支重复拼接与潜在规则漂移。

### A12：公开技能包解压入口信任上层预先校验 skill_id

- 事实链：`download::archive` 是公开模块，`extract_skill_package_zip` 也是公开函数，但函数自身未验证 `expected_skill_id`。内部两个管理器调用点此前已先校验，因此正常产品链路不触发；公开调用者若传入空 ZIP、`../outside`，且临时根外恰好已有 `outside/skill.yaml`，旧函数的最终 `temp_root.join(expected_skill_id)` 探测会把根外目录当成成功解压结果返回。

### A13：ZIP 导出匹配命中后使用了不存在的规范化条目名

- 分类：实际功能 BUG，必须修改。
- 事实链：`resolve_zip_export_entry_name` 会把条目中的反斜杠规范为正斜杠，并支持剥离一层顶层目录进行匹配；但命中后返回的是规范化字符串，不是 ZIP 中的原始名称。调用方随后执行要求精确原始名称的 `archive.by_name`，因此 `package\bin\demo.exe` 可以先匹配 `bin/demo.exe`，再以不存在的 `package/bin/demo.exe` 读取失败。
- 修复：匹配仍使用统一规范化表示，但返回并传给 `by_name` 的值改为迭代器提供的真实条目名称；精确匹配和剥离顶层目录两个分支统一处理。
- 修改后收益：原本已经声明支持的分隔符归一化与单层包目录兼容真正生效；标准 ZIP 名称的行为完全不变，没有增加新的归档格式或模糊候选规则。
- 复验：运行时生成包含 `package\bin\demo.exe` 的 ZIP，以 `bin/demo.exe` 声明安装并验证输出字节完全一致；测试 1 项通过。

### A14：显式关闭托管临时文件时吞掉删除失败

- 分类：实际资源与 API 结果 BUG，必须修改。
- 事实链：`ManagedIoFile::close` 在成功刷新后，对 `delete_on_close` 路径执行 `let _ = fs::remove_file(...)`，无论权限、路径类型或底层文件系统错误都继续把句柄标记为关闭并返回成功。该位置是 Lua 可显式调用的 `file:close()`，不是无法返回错误的 Drop；失败会泄漏临时文件且关闭状态阻止调用方重试。
- 修复：删除成功或目标已经不存在时继续关闭；其他删除错误转换为 `file:close` 运行时错误，并保持 `closed=false` 以允许纠正环境后重试。
- 修改后收益：显式关闭结果与临时文件生命周期一致，资源泄漏不再被伪装成成功；普通文件、正常临时文件和幂等关闭语义保持不变。
- 约束：本次只处理删除错误保真；更新模式每次 flush 重写整缓冲仍是已列入次级方案的 P05，不在此处扩大重构。
- 复验：以目录占据待删除路径，使 flush 成功但 `remove_file` 确定性失败；测试确认错误可见且句柄未标记关闭，1 项通过。

### A15：tar.gz 用磁盘旧文件冒充本次导出命中，且同源多目标只处理首项

- 分类：实际安装完整性与功能 BUG，必须修改；同时移除误导性的事后验证。
- 事实链：tar.gz 分支流式遍历后没有保存每个声明是否由本次归档产出，而是对最终目标执行 `metadata.is_file()`。部分旧安装中的普通文件可以满足新归档中缺失的条目，形成新旧文件混装并返回成功；匹配时使用 `.find(...)`，同一 `archive_path` 声明到多个合法目标时仅写第一个，第二个只能依赖旧文件或报缺失。ZIP 分支逐声明读取，不存在这两个问题。
- 修复：安装前为全部导出声明建立顺序一致的命中表；每个 tar 条目收集全部匹配声明，首个目标继续直接流式接收条目，关闭输出句柄后由首个目标文件复制到其余目标；完成后只依据本次命中表判定完整性，不再用磁盘存在性推断归档内容。
- 修改后收益：陈旧文件不能让不完整归档通过，安装结果真实对应下载载荷；同源多目标契约与 ZIP 分支一致，同时保持 A06 的整包/整条目流式内存边界。
- 连带影响：过去依赖旧文件补齐缺失 tar 条目的非规范安装会失败并触发既有清理、重下载流程，这是完整性修复而非兼容性回退。
- 复验：一项测试构造已存在普通目标文件但归档缺失声明，确认明确失败且旧文件未被改写；另一项测试用单个 tar 条目导出到两个目录并逐字节验证，归档模块共 11 项通过。

### A16：依赖检测把任意已存在路径当成就绪导出

- 分类：实际功能与恢复逻辑 BUG，必须修改。
- 事实链：`detect_dependency` 的共享 helper 仅调用 `Path::try_exists()`；目录、叶子符号链接和 Unix 上缺少执行位的普通文件都会返回 true。目录会让依赖被永久跳过，chmod 失败留下的不可执行工具也会在下一次启动被视为已安装，`DependencyExportSpec.executable` 在检测阶段完全失效。
- 修复：单次 `symlink_metadata` 同时完成缺失、类型与错误判断；只有非符号链接普通文件可进入就绪状态，Unix 的可执行声明还要求至少一个执行位。缺失、类型和模式不符返回 `Missing` 进入既有安装恢复链，权限/非法路径等真实探测错误继续显式返回。
- 修改后收益：依赖存在性与实际可用性一致，损坏目标可以由现有下载/清理/重装流程恢复；不增加 metadata 预检次数，也不把探测错误误导成缺失。
- 平台边界：目录恢复测试已在 Windows 实际通过；Unix 执行位测试以 `#[cfg(unix)]` 编译运行，当前 Windows 主机无法声称其实机通过，最终跨平台 CI 应执行该项。
- 复验：目录占据导出路径时返回 `DependencyDetectionStatus::Missing`；原有内嵌 NUL 探测错误测试继续通过。

### A17：依赖安装会跟随预先存在的目标或父目录符号链接

- 分类：实际安全 BUG，必须修改；属于 A11 路径归属边界的磁盘状态补全。
- 事实链：A11 只关闭了清单字符串的词法逃逸；`fs::copy`、`File::create` 与 `create_dir_all` 仍会跟随磁盘上已经存在的叶子链接或父目录链接。A16 正确把叶子链接判成 Missing 后，安装分支反而会立即跟随该链接写入其指向位置，形成依赖根外覆盖。
- 修复：全部目标完成词法解析后、创建任何目录或复制载荷前，逐个从安装根向叶子检查现存路径片段；父组件必须是非链接目录，现存叶子必须是非链接普通文件，缺失片段允许后续创建，探测失败显式返回。三类载荷共享该全局边界，不在各分支重复实现。
- 修改后收益：预先布置的叶子链接和父目录链接不能把依赖载荷重定向到管理根之外；普通覆盖与全新目录创建保持原语义。
- 约束：该检查关闭静态磁盘状态攻击，不宣称消除检查与打开之间由并发本地攻击者制造的 TOCTOU；彻底无跟随需要 Unix `openat2`/Windows 重解析点句柄级实现，应作为独立跨平台安全架构决策。
- 复验：跨平台测试在宿主允许创建文件符号链接时构造根外指向，确认安装明确失败且根外字节不变；当前聚焦测试通过，不支持创建链接的平台按现有测试约定跳过夹具。

### A18：公开 DependencyManager 接口未独立验证 skill_id

- 分类：实际安全 BUG，必须修改；与 A12 同属公开 API 信任上层的问题。
- 事实链：`ensure_skill_dependencies`、卸载清理和更新清理都是公开方法，`skill_id` 会直接进入 `root.join(skill_id)`。引擎内部调用已验证目录名，但外部 crate 调用可传 `../protected`；尤其 `cleanup_uninstalled_skill_dependencies_from_roots` 会在三个依赖配置根上递归删除该拼接路径，能够越界删除同级目录。
- 修复：安装入口、最内层公开卸载清理入口和公开更新清理入口均在首个扫描/下载/删除动作前调用统一 `validate_luaskills_identifier`；外层卸载便利方法复用最内层校验，不重复验证。
- 修改后收益：公开依赖管理契约自行维持路径归属，不再依赖调用顺序或引擎私有事实；内部合法调用无行为变化。
- 复验：空依赖清单配 `../outside` 在任何副作用前失败；构造旧逻辑会解析到的同级 `protected/keep.txt` 后调用公开卸载清理，确认错误返回且标记文件仍存在；依赖管理器 22 项测试通过。

### A19：依赖名称/版本规范化允许 `..` 逃逸且会发生身份碰撞

- 分类：实际安全与依赖身份完整性 BUG，必须修改。
- 事实链：`normalize_dependency_path_component` 允许点号，因此原始值恰好为 `.` 或 `..` 时原样进入 `root.join(...)`；依赖名称或版本可直接改变安装根归属。其他所有非法字符统一替换为 `_`，使 `a/b` 与 `a?b` 等不同依赖/版本共享目录并互相满足检测或覆盖。名称来自技能清单，版本还可能来自远程 Release，现有类型没有更早的唯一安全语法约束。
- 修复：完全安全、非特殊、非 Windows 设备名的 ASCII 组件保持原样，维持常见名称与 SemVer 路径；空值、`.`/`..`、分隔符/其他非法字符、末尾点号以及 Windows 保留设备主干统一改为原始 UTF-8 字节的完整 SHA-256 目录组件。
- 修改后收益：任何输入只形成一个普通安全组件，特殊名称/版本不能越界；不同不安全原始值不再因替换规则碰撞，共享根仍只发生在原始身份相同的情况下。
- 连带影响：历史上含 `+`、空格、Unicode 或其他非白名单字符的依赖名称/版本会迁移到摘要路径，首次升级可能重新下载且旧目录需后续清理；常见 `rg`、`v1.2.3` 等路径完全不变。
- 复验：覆盖空值、`.`、`..`、正反分隔符、`CON`、`nul.txt`、末尾点号和碰撞输入；构造名称与版本双 `..` 的安装根并确认根后只有三个普通片段；全部依赖管理器 24 项测试通过。

### A20：公开的已准备技能事务对象允许调用方伪造递归删除路径

- 分类：实际安全与 API 所有权 BUG，必须修改；不是功能扩展。
- 事实链：`PreparedSkillInstall`、`PreparedSkillUpdate`、`PreparedSkillUninstall` 是公开结构体，所有路径与安装记录字段也全部公开；外部 crate 可以构造或篡改这些对象，再传给公开的 `commit_prepared_skill_*` / `rollback_prepared_skill_*`。这些方法会对对象中的 `target_dir` / `backup_dir` 直接执行 `remove_dir_all` 或 `rename`，没有重新确认路径是否由当前 `SkillManager` 产生，因此公开数据对象实际携带了可伪造的磁盘删除能力。
- 修复：保留已准备事务类型、结果字段和两阶段提交 API 的公开可用性；把所有路径及内部安装/停用记录字段收紧为 `pub(crate)`。事务仍只能由管理器的 `prepare_*` 方法产生，外部调用方可以把返回对象交还给提交/回滚入口，但不能读取、构造或替换内部磁盘路径。
- 修改后收益：递归删除和重命名目标重新绑定到 crate 内已经校验并暂存的事务事实；不再允许安全边界外的调用方把任意宿主路径包装成“已准备事务”。正常运行时两阶段事务及公开结果读取行为保持不变。
- 连带影响：这是有意的 API 收紧；过去直接读取内部路径/安装记录字段或手工构造事务对象的外部代码将不再编译。这些字段本来就是提交协议的内部能力数据，继续公开会产生误导和安全风险，因此该兼容性变化是必要的。
- 复验：临时外部 crate 引用当前仓库并读取 `PreparedSkillUninstall.target_dir`，编译稳定返回 `E0616: private field`；探针随后已删除。技能管理器 44 项测试通过，严格 Clippy 通过。

### A21：本轮依赖检测的非 Unix 分支产生未使用变量，现有 mlua 类型别名已弃用

- 分类：工程与兼容性修复；不是运行时 BUG，也没有增加功能，但属于最终零告警门禁前必须处理的问题。
- 事实链：A16 新增的 `metadata` 仅在 `#[cfg(unix)]` 分支读取，Windows 的 `cargo check` 报告未使用变量；同时当前 mlua 版本已把 `mlua::String` 标记为弃用，运行时引擎和 lease 共 6 个类型标注仍使用旧别名。外部可见性编译探针实际复现了 1 个 unused 和 6 个 deprecated 告警。
- 修复：非 Unix 分支显式消费 `metadata` 与 `executable`，保持平台语义不变；6 处类型标注机械替换为官方现行的 `mlua::LuaString`，没有转换、生命周期或数据流变化。
- 修改后收益：当前 Windows 构建恢复零告警，避免严格 `-D warnings` 阻断；同时提前消除 mlua 后续移除旧别名时的编译风险。
- 复验：`cargo clippy --all-targets --all-features -- -D warnings` 返回 `No issues found`。

### A22：带路径的公开卸载入口可暂存并删除管理技能根之外的任意目录

- 分类：实际安全与 API 归属 BUG，必须修改；与 A20 相邻但攻击入口独立存在。
- 事实链：`prepare_uninstall_skill_at_path_in_plane` 是公开方法，`skill_id` 会经过生命周期守卫校验，但调用方传入的 `skill_dir` 只经过“是否为目录”探测。只要传入任意现存目录，该方法就会把目录重命名进生命周期备份区，后续提交再递归删除；引擎内部唯一调用传入的是从当前命名技能根解析出的 `actual_dir`，而 `collect_named_skill_dirs` 证明该目录唯一等于当前管理器的 `skills_dir/<skill_id>`。
- 修复：在生命周期状态创建、目录探测、重命名之前构造当前管理器唯一拥有的 `skills_dir/<skill_id>`，要求带路径入口的实参与该路径严格一致；不一致时返回包含实际路径与预期路径的显式错误。
- 修改后收益：公开入口不能再把管理器之外的目录转化成待提交卸载事务；内部多技能根卸载继续由对应根的 `SkillManager` 处理，行为不变。
- 连带影响：过去把同一目录写成带 `.`、不同绝对/相对形式，或故意传入别的技能根的外部调用会被拒绝。调用方应使用管理器配置中的规范根路径，或直接使用不接收路径的 `uninstall_skill*` 入口；这是消除模糊归属所需的有意约束。
- 复验：新增根外 `protected/keep.txt` 回归测试，调用带路径准备卸载后得到 `unmanaged directory`，标记仍存在且生命周期状态目录尚未创建；技能管理器 45 项测试通过。

### A23：配置原子写入失败时吞掉临时文件清理错误

- 分类：实际资源泄漏与诊断 BUG，必须修改；不是功能扩展。
- 事实链：`SkillConfigStore::write_document_to` 在临时文件写入/同步失败和原子发布失败两个分支都执行 `let _cleanup_result = fs::remove_file(...)`。清理失败时主配置文件虽未被错误覆盖，但不可删除的随机临时文件会残留，调用方只能看到最初错误，无法知道磁盘仍需人工处理；重复失败可以持续累积残留。
- 修复：新增唯一共享的失败清理函数；删除成功或目标已不存在时原样保留主错误，真实删除失败时把临时路径和清理错误追加到同一返回值。两个失败分支统一复用该函数，不增加第二套错误策略。
- 修改后收益：主失败因果保持稳定，同时磁盘残留从静默状态变成可诊断状态；运维可依据精确路径清理，不会把失败误解为完全无残留。
- 连带影响：只有“主操作失败且临时文件清理也失败”的错误文本会增加第二段诊断；成功提交、主失败但清理成功、临时文件本就不存在的返回语义均不变。
- 复验：确定性地用目录占据临时文件路径，使 `remove_file` 失败；测试确认返回值同时包含主错误、清理错误和宿主可见路径，目标仍在以证明失败真实发生。配置模块 33 项测试通过。

### A24：脚本把网络、API 与摘要失败误导为“资产不存在”并静默使用旧内容

- 分类：实际完整性与诊断 BUG，必须修改；同时属于用户要求识别的误导性问题。
- 事实链：Bash 的 `save_release_asset_with_digest` 通过进程替换向 `mapfile` 取值，子命令失败状态不会成为 `mapfile` 的状态；PowerShell 的安装器则用无类型 `catch` 捕获整个查询、下载和摘要链。两端只要运行根已有旧内容，就会把 Release 不存在、网络失败、JSON 失败、摘要缺失和 SHA-256 不匹配全部警告成“asset was not found”，随后返回成功继续使用旧文件。完整性失败因此能被错误降级，真实原因也被错误文本覆盖。
- 修复：Bash 改为直接捕获查询命令替换状态，只有查询函数的精确“资产缺失”状态 2 可以触发旧内容兼容回退，其他查询/下载/摘要失败统一返回硬错误；PowerShell 新增专用 `ReleaseAssetNotFoundException`，只有 `Get-ReleaseAssetInfo` 确认资产列表中不存在精确名称时抛出并被兼容分支捕获，其他异常不再被捕获。依赖运行包和 FFI SDK 两套 Bash/PowerShell 脚本保持一致。
- 修改后收益：完整性校验恢复为不可降级门禁，网络与 API 故障保留真实诊断；已有打包内容只在远端 Release 确实未发布对应可选资产时继续使用。
- 连带影响：过去网络临时故障或摘要不匹配时会继续运行旧内容，现在会终止安装；这是避免供应链错误被误报为兼容回退所必需的行为收紧。
- 复验：两个 Bash 下载函数均用函数级动态探针验证精确缺失返回 2、查询失败返回 1、摘要不匹配返回 1；两份 Bash 通过 `bash -n`，两份 PowerShell 通过 AST Parser，临时探针已删除。

### A25：PowerShell 安装脚本静默忽略已校验归档的复制失败

- 分类：实际部分安装与误报成功 BUG，必须修改；不是功能扩展。
- 事实链：`fetch_deps.ps1` 复制 `lua_packages/resources/libs/licenses`，以及 `fetch_ffi.ps1` 复制 `include/lib/licenses` 时显式使用 `-ErrorAction SilentlyContinue`。即使脚本全局设置 `ErrorActionPreference=Stop`，这些调用仍会覆盖全局策略；权限、磁盘空间、占用等复制错误可被吞掉。后续只检查少数目标文件，未被检查的文件缺失不会使脚本失败。
- 修复：5 个发布内容复制点全部改为 `-ErrorAction Stop`；临时目录最终清理仍保留最佳努力语义，不与发布复制混为一谈。
- 修改后收益：PowerShell 与 `set -e` 的 Bash 路径语义一致；任何归档内容复制失败都会中止安装并保留原生错误，不再报告一个不完整运行时为成功。
- 连带影响：过去可能依赖“尽量复制、缺文件也继续”的调用现在会显式失败；发布安装契约要求完整内容，因此该变化是必要修复。
- 复验：两份 PowerShell 脚本均通过 AST Parser；仓库扫描确认这 5 个发布复制点不再存在 `SilentlyContinue`。

### A26：安装后目标检查可被旧 manifest/动态库满足，格式错误的新归档仍成功

- 分类：实际陈旧状态掩盖与部分发布 BUG，必须修改；属于逻辑性修复而非扩展。
- 事实链：运行包和 FFI 安装器先把解压内容合并进已有运行根，之后才检查目标根中的 manifest 或动态库。若新归档缺少这些必需文件，但目标根保留旧版本对应文件，检查仍会通过；其他新文件甚至已经部分覆盖，形成版本混合。Bash 与 PowerShell 都存在相同行为。
- 修复：所有必需契约统一前移到任何复制之前：运行包必须在解压源中包含 `lua_packages`，完整模式还必须包含两个 `resources` manifest；FFI SDK 必须在解压源 `lib` 中包含当前平台候选核心库之一。源校验通过后复制错误已由 A25/`set -e` 保证传播，因此删除依赖目标旧状态的重复后置检查。
- 修改后收益：格式错误的归档在零目标写入时失败，旧文件不能再替新归档证明完整；避免同一运行根出现新旧混合发布，同时减少没有独立价值的重复目标验证。
- 连带影响：过去允许“只含部分目录、其余由旧安装补齐”的归档会被拒绝；明确的远端资产缺失仍可按 A24 走已有内容兼容回退，两种情形不再混淆。
- 复验：Bash 动态探针分别构造“有新 lua_packages 但无源 manifest、目标已有旧 manifest”和“有新 header 但无源动态库、目标已有旧动态库”的摘要已接受归档；两次都在复制前失败，旧标记保持、新文件未出现。两份 Bash 通过 `bash -n`，两份 PowerShell 通过 AST Parser。

### A27：受管运行时缓存只检查 manifest 或入口的一半，残缺安装会被永久复用

- 分类：实际缓存就绪判断与恢复 BUG，必须修改；同时消除四个分支各自不完整的验证逻辑。
- 事实链：uv、Node、pnpm 的非强制分支只检查入口文件是否存在，不检查 `runtime-manifest.json`；Python 只检查 manifest 是否存在，不检查清单身份、入口归属与解释器文件。入口/清单任一半缺失、JSON 损坏、版本/平台不匹配或入口指向根外时，旧逻辑可能直接返回，也可能在后续把新目录移动进残缺的已有目标，导致永远无法自愈或发布失败。
- 修复：Bash 与 PowerShell 各新增一个共享就绪解析器，统一验证 schema、runtime、version、platform、相对入口声明、入口根内归属和真实文件存在；uv/Node/pnpm 还要求精确入口字段。四个安装分支只有共享解析器返回入口时才复用，否则删除其确定性的版本化受管目录并进入正常重装。
- 修改后收益：所有运行时使用同一个完整就绪定义，不再出现“文件存在即可”与“manifest 存在即可”的分支漂移；残缺缓存自动恢复，错误身份或根外入口不能成为跳过安装的依据。
- 连带影响：手工放置可执行文件但不生成合法 manifest、或手工保留 manifest 但删除入口的目录会被视为损坏并重装；这是受管目录所有权契约的必要收紧。Bash 会同时要求实际执行入口具备执行位，PowerShell 当前主机验证普通文件存在并由后续版本命令验证可运行。
- 复验：Bash 从生产脚本提取精确 helper，验证匹配身份+根内入口成功、版本不匹配失败、`../outside` 即使外部文件存在也失败；PowerShell 通过生产 AST 提取同一 helper，完成匹配与逃逸动态探针。Bash `-n` 与 PowerShell Parser 均通过；临时探针及外部标记均已删除。

### A28：全量并行测试中的 PATH 竞态与过短超时夹具导致伪失败

- 分类：实际测试可靠性 BUG，必须修改；不改变生产功能。
- 事实链：正式复审第 1 轮的全目标测试得到 665 通过、2 失败、3 忽略。`direct_child_reaping_is_bounded_by_absolute_deadline` 通过 PATH 启动 PowerShell，却没有获取仓库统一的进程环境锁，能与修改 PATH 的测试并发而报 `program not found`。`process.exec` 超时测试只让夹具存活约 1～2 秒；全套件线程受压时，测试线程在首次轮询前可能被调度暂停到夹具自然退出，从而得到 `timed_out=false`。两项单独运行均通过，证明属于并行/调度夹具不确定性而非产品超时逻辑稳定失败。
- 修复：PATH 解析子进程的测试在 spawn 前获取 `process_env_test_guard`；超时夹具改为 Windows 约 30 秒 ping / Unix `sleep 30`，仍由 50ms 生产超时立即终止，因此正常测试耗时不增加到 30 秒。
- 修改后收益：PATH 读者与修改者纳入同一进程级串行边界；即使全套件线程被调度暂停数秒，超时夹具仍不会先自然结束，测试真正验证产品超时而不是宿主调度速度。
- 连带影响：仅测试夹具寿命变长，生产 API 与测试正常完成时长不变；若产品终止逻辑回归，测试最多会由现有进程回收上界控制，而不是静默等待完整 30 秒。
- 复验：两项测试分别精确运行均通过；发现问题后正式连续计数保持清零，必须重跑全量测试后才能开始累计。

### 5.4 P02/P22 确定性调度证据

- P02 修改后：首次检查后由输出代次变化唤醒；无新输出时新增扫描为 0，发生追加时只线性化“未扫描字节 + 编码/marker 重叠窗口”。跨 UTF-8、GB18030、Base64 边界和环形淘汰均有测试。
- P22 修改前：1/32/256 个 observer 会话分别增加 1/32/256 个固定 10ms ExitWatcher 线程，空闲探测上界约 100/3200/25600 次每秒。
- P22 修改后：1/32/256 个会话均只启动 1 个进程级 watcher 线程；稳定空闲后每会话 250ms 探测一次，上界约 4/128/1024 次每秒。
- 延迟权衡：修改前空闲退出发现延迟约 10ms；修改后最坏约 250ms，注册与终态变化会把退避重置为 10ms。该权衡符合优先方案允许的自适应退避边界，但不是零代价优化。
- 未直接测量项：没有独立性能计数器可可靠隔离 watcher 的 CPU 占用，因此只记录已由测试证明的线程数与确定性探测上界，不伪造 CPU 百分比。
