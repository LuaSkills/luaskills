## 分类口径

### 实际 BUG

满足以下任一条件：已有路径直接失败；配置被静默忽略；资源随外部输入无界增长；已锁定依赖存在公开漏洞；进程级对象在可变租户/路径集合下永久泄漏。BUG 不要求已有单元测试失败，因为现有测试可能没有覆盖故障触发条件。

### 逻辑性修复或优化

外部语义目前仍可正确完成，但实现存在可证实的重复复制、重复序列化、重复哈希、全量扫描、锁内重操作、无效线程或 I/O 放大。此类问题需要把“模式已存在”和“收益已量化”分开：本轮确认实现模式，未对所有项建立性能基准。

### 扩展

原接口没有某个可配置能力、诊断字段、测试分类或性能门禁，修复时需要新增对外或工程能力。扩展不是原 BUG 本身，不能把增加配置/API 与内部修复混为一谈。

### 条件项与误导性建议

重复现象确实存在，但可能服务于示例自包含、跨平台验收、安全竞态关闭或 ABI 释放契约。缺少量化或契约确认时，不应直接删除、集中化或强制合并。

### 必须性标记

- **必须**：现有功能失效、安全/资源无界、静默配置错误或发布门禁配置错误。
- **应改**：收益和事实链明确，但不修复不会立即产生错误结果。
- **条件修改**：需先满足规模、基准、契约或政策前提。
- **不建议直接修改**：当前建议的风险大于已证明收益，应先保留或测量。

## 实际 BUG 的修改收益

### P24：依赖漏洞

- 修改性质：安全修复。
- 修改后：阻断已知的 HTTP/2 空 DATA 帧无界队列与溢出 panic 路径。
- 不修改：下载和控制器 gRPC 依赖图继续包含公开漏洞，依赖门禁持续失败。

### P23：popen 无界捕获

- 修改性质：资源安全修复；stdout 限额部分是扩展。
- 修改后：至少消除“完整保存后丢弃 stderr”的无效内存链；增加限额后可约束异常命令的最大捕获内存。
- 不修改：大输出命令仍可让宿主内存随输出量增长，超时也不能回收已经分配的峰值。

### P13：全局缓存配置静默失效

- 修改性质：配置语义修复。
- 修改后：后续引擎不再得到“配置被接受”的错误表象；冲突会显式失败或遵循明确的进程全局契约。
- 不修改：多引擎宿主可能以为隔离配置已经生效，实际持续使用首个引擎的缓存容量与 TTL。

### P12：配置路径锁注册表泄漏

- 修改性质：生命周期修复。
- 修改后：不再永久持有历史配置路径与锁对象。
- 不修改：长生命周期、动态配置根进程的注册表只增不减。

### A01：demo 入口失效

- 修改性质：功能 BUG 修复。
- 修改后：四个 launcher 的依赖拉取分支恢复可执行。
- 不修改：默认 `none` 可能掩盖问题，但任何实际 fetch 请求都会立即失败。

### A02 的 BUG 子项

- 修改性质：依赖治理配置修复。
- 修改后：删除已经不匹配上游包元数据、且文件不存在的 clarification，减少门禁噪声。
- 不修改：许可证检查持续包含陈旧错误，掩盖真正需要维护者判断的 CC0 政策问题。

## 扩展项

以下内容不是原问题的“修 BUG 最小改动”，应单独设计、验收和版本化：

1. **X01：popen 输出预算**：为 stdout 增加宿主管控的最大捕获字节、截断标记/错误码；可选保留有界 stderr 尾部用于诊断。预期把内存上界变成可配置常数，但会改变完整输出契约。
2. **X02：CI 测试分类**：新增通用、平台路径、原生会话、动态库、进程树等显式 test target/tag。预期在保持覆盖的前提下降低矩阵重复，但新增分类本身需要持续维护。
3. **X03：性能与产物基线**：增加 VM 冷启动、until_text、并发会话、Managed IO、下载峰值内存、控制器并发及 release 体积基线。预期把“源码上可见的低效”升级为可防回归的量化门禁。
4. **X04：每引擎 Tool Cache**：只有产品明确要求引擎级隔离时才实施。它会改变当前进程全局缓存的共享范围，属于架构扩展；若没有该需求，最小修复是显式进程全局配置与冲突诊断。

## 必须修改、连带修改与误导性项

### 必须修改

1. `P24`：公开漏洞且门禁直接失败。
2. `P23`：先处理无产出的无界 stderr 捕获；stdout 预算作为后续扩展。
3. `A01`：已有 launcher 分支直接失效。
4. `P13`：宿主配置静默不生效。
5. `P12`：进程级历史路径强引用不回收。
6. `A02` 的陈旧 clarification；CC0 是否允许必须由维护者决策。

### 修改会产生较大连带影响

- `P01`：会改变控制器真实并发度和关闭竞争。
- `P02`：会改变输出通知、编码边界和 marker 搜索实现。
- `P03`：会改变技能加载代、debug 热更新和 VM 快照生命周期。
- `P04`：错误缓存会破坏资产完整性与更新可见性。
- `P05`：会影响 seek/update/flush/close 的文件语义。
- `P06`：错误的所有权转移会造成 FFI 未定义行为，若改结构则影响 ABI。
- `P07-P08`：会改变 client 生命周期、缓存发布、并发下载和 Windows 替换语义。
- `P13`：必须在“进程全局”与“每引擎”之间做明确契约选择。
- `P21`：拆分不当会损失跨平台回归覆盖。
- `P22`：会影响跨平台进程等待和退出事件时序。
- `P23`：stdout 截断会改变调用者可见输出。
- `P24`：依赖升级需要验证 HTTP 与 gRPC 两条链路。

### 具有误导性的直接建议

- `P04`：把所有重复验证全部删除——错误，锁内二次检查是必要安全边界。
- `P06`：把任意 String/Vec 直接塞入现有 `ptr + len` buffer——可能导致释放时 capacity 不匹配。
- `P11`：立即引入复杂索引——默认最多 1000 项，应先做低复杂度修复与基准。
- `P14`：简单删除第二次校验——应改为一次返回 Metadata，而不是降低检查信息。
- `P16`：为了四个小入口强制建立共享运行时 helper——当前可能增加耦合而没有可测收益。
- `P17`：为了消除重复让示例依赖复杂公共框架——会损害示例自包含。
- `P18`：让发布包脚本运行时引用仓库 helper——会破坏独立分发。
- `P21`：立刻只在一个平台跑全量测试——在没有测试分类前会丢失覆盖。
- `P23`：停止读取仍保持 piped stderr——管道可能写满并阻塞子进程；应使用 null 或有界 drain。
- `P25`：按锁文件重复版本强制 patch——未证明进入同一产物，且可能合并不兼容主版本。
- `A02`：为通过门禁自动允许 CC0——许可证接受必须由项目维护者决定。

## 最终修复顺序建议

### 阶段 0：先完成必须的政策确认

1. 确认项目是否接受 `CC0-1.0`。这不是技术智能体可替代的许可证决策。

### 阶段 1：安全、直接失效与静默错误

1. `P24`：把 `h2` 更新到 0.4.16 及以上，跑全目标测试、真实下载和控制器 gRPC 验收。
2. `A01`：修复四个 launcher 路径，并加不联网的参数/路径 smoke。
3. `A02`：删除或更新陈旧 clarification；按阶段 0 的决定处理 notify 许可证策略，复跑 `cargo deny check`。
4. `P23` 第一阶段：stderr 改为 null 或有界尾部；保留 stdout 现有完整返回语义。
5. `P13`：先定义 Tool Cache 为进程全局还是每引擎；最小方案是进程全局一次初始化并显式拒绝冲突。
6. `P12`：将配置路径锁注册表改为 Weak 并清理失效项。

### 阶段 2：低风险、可独立验收的逻辑优化

1. `P09`：JSON 响应一次序列化。
2. `P10`：配置包一次解析和复用。
3. `P14`：缓存探测直接返回 Metadata/长度。
4. `P15`：Lua VM 锁内摘除、锁外析构。
5. `P11`：精确删除过期键和摊销清理；先不引入复杂多索引。

### 阶段 3：高收益并发与资源优化

1. `P01`：解除控制器全局 Runtime 互斥，先补并发/关闭回归测试。
2. `P02`：输出通知加增量 marker 搜索。
3. `P22`：集中退出 reaper/有限 worker，和 P02 共用明确的会话唤醒、关闭设计边界。
4. `P07-P08`：一起重构下载栈，复用 blocking client/worker，同时流式写入、同步哈希、临时文件发布。
5. `P05`：按 Write、Append、Update 分开设计 flush，不做单一策略替换。
6. `P03`：引入加载代不可变快照；非 debug 缓存源码，debug 保持热重读。
7. `P04`：在加载代/owner token 生命周期稳定后再缓存解析计划，保留临近使用和锁内校验。

### 阶段 4：ABI、构建与工程扩展

1. `P06`：优先用 boxed slice/精确容量在现有 ABI 内消除复制；若改结构，单独发布 ABI 版本。
2. `P19-P20`：在记录 bundle 大小和打包耗时后，实施流式构建下载与共享依赖闭包扫描。
3. `P18`：只抽取仓库源码 helper，发布产物继续自包含。
4. `X01`：设计 popen stdout 预算与截断诊断。
5. `X02`：建立 CI 测试分类后，再决定 `P21` 的矩阵拆分。
6. `X03`：建立性能和产物基线后，再决定 `P25` 是否有可操作的依赖统一收益。

### 暂不安排修改

- `P16`：保持四个小型 Hub 入口独立，除非入口数量或协议漂移显著增长。
- `P17`：保持示例自包含，除非 ABI helper 已出现真实漂移。
- `P21`：在测试分类和覆盖映射完成前不削减矩阵全量测试。
- `P25`：在 release 目标体积/链接 map 与干净构建基线完成前不强制统一依赖。
